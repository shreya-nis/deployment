## 1. Architecture Overview

When a user visits your website, requests flow through the AWS EC2 instance as follows:

```
                            [ USER / BROWSER ]
                                    │
                                    │ HTTP Request (Port 80)
                                    ▼
                  ┌───────────────────────────────────┐
                  │          AWS EC2 INSTANCE         │
                  │         (Ubuntu 24.04 LTS)        │
                  │                                   │
                  │   ┌───────────────────────────┐   │
                  │   │    NGINX (Reverse Proxy)  │   │
                  │   └─────────────┬─────────────┘   │
                  │                 │                 │
                  │    ┌────────────┴───────────┐     │
                  │    │                        │     │
                  │    ▼                        ▼     │
                  │  Static Files           Backend   │
                  │  (Frontend React)       API (PM2) │
                  │  /var/www/app/frontend  Port 5000 │
                  │  /dist                            │
                  └─────────────────────────────┬─────┘
                                                │
                                                │ Database Connection
                                                ▼
                                    [ CLOUD DATABASE ]
                                    (MongoDB Atlas M0 - 24/7)
```

### Key Pillars of this Setup:
- **AWS CloudFormation (Infrastructure-as-Code):** The entire EC2 instance, security group (Ports 80 & 22), and SSH key pair are defined declaratively in `infra/ec2-instance.yaml`. No manual clicks in AWS console.
- **AWS SSM Parameter Store:** The private SSH key generated by CloudFormation is securely stored in AWS Systems Manager (`/ec2/keypair/*`). GitHub Actions retrieves it dynamically on each deploy without storing static private keys.
- **Nginx Web Server:** Listens on standard HTTP port 80. Serves pre-compiled React static assets with client-side routing fallback (`try_files $uri $uri/ /index.html`), reverse-proxies `/api/` and `/uploads/` to Express.
- **PM2 Process Manager:** Runs the backend on port 5000 in `fork` mode (optimized for single-core `t2.micro` instances) and automatically revives the service if the node process crashes or machine restarts.
- **GitHub Actions CI/CD:** Automatically triggers on every push to `main`: builds frontend, deploys CloudFormation stack, connects via SSH, syncs code, creates production `.env`, builds the frontend on the server, and restarts PM2 and Nginx.

## 3. The 4 Infrastructure Files Implemented

### File 1: CloudFormation Infrastructure (`infra/ec2-instance.yaml`)
Provisions:
1. `ServerKeyPair`: Automatic EC2 KeyPair saved to SSM Parameter Store (`/ec2/keypair/${ServerKeyPair.KeyPairId}`).
2. `ServerSecurityGroup`: Opens Port 80 (HTTP) to `0.0.0.0/0` and Port 22 (SSH) to `0.0.0.0/0`.
3. `ServerInstance`: Ubuntu 24.04 LTS `t2.micro` instance with UserData bootstrapping (installs Node.js 22, Git, Nginx, PM2, prepares `/var/www/app`).
4. Outputs: `PublicIP`, `PublicURL`, and `SSMKeyPath`.

### File 2: Nginx Web Server & Reverse Proxy (`infra/nginx.conf`)
- **Frontend SPA routing:** Points `root` to `/var/www/app/frontend/dist` and uses `try_files $uri $uri/ /index.html;` to ensure page refreshes on React Router paths (e.g., `/shop`, `/cart`, `/admin`) do not return 404.
- **Backend API Reverse Proxy:** Proxies `/api/` to `http://127.0.0.1:5000/api/` with HTTP/1.1 headers.
- **Uploads Reverse Proxy:** Uses `location ^~ /uploads/` with the `^~` priority modifier to guarantee media uploads are proxied to Express and not caught by static file regexes.
- **Static Asset Caching:** Caches static files (`.js`, `.css`, images, fonts) for 30 days.

### File 3: PM2 Process Manager (`backend/ecosystem.config.cjs`)
- Name: `skincare-backend`
- Entry: `server.js`
- Working Directory: `/var/www/app/backend`
- `exec_mode: 'fork'` and `instances: 1` (avoids CPU thrashing and memory crash loops on single-core `t2.micro`).
- `max_memory_restart: '300M'` to prevent Out-Of-Memory termination on 1GB RAM instances.

### File 4: GitHub Actions CI/CD Pipeline (`.github/workflows/deploy.yml`)
Runs two jobs on every push to `main`:
1. **`build` job:** Checks out code, sets up Node.js 22, builds frontend with `VITE_API_URL: /api` to ensure bundle compiles before server changes.
2. **`deploy` job:**
   - Authenticates to AWS via `aws-actions/configure-aws-credentials@v4`.
   - Deploys or updates the CloudFormation stack `skincare-app-stack`.
   - Queries `PublicIP` and `SSMKeyPath` from CloudFormation outputs.
   - Retrieves the private SSH key from AWS SSM Parameter Store on-the-fly into `/tmp/server-key.pem`.
   - Waits for SSH port 22 availability.
   - Connects to EC2 using `appleboy/ssh-action@v1.2.0` and executes:
     - Waits for cloud-init bootstrap to finish (`cloud-init status --wait`).
     - Clones or pulls the latest code to `/var/www/app`.
     - Installs backend production dependencies (`npm ci --omit=dev`).
     - Writes backend `.env` securely from GitHub Secrets (`PORT`, `NODE_ENV`, `CLIENT_URL`, `MONGO_URI`, `MONGODB_URI`, `JWT_SECRET`).
     - Builds the frontend bundle (`npm run build`).
     - Reloads PM2 (`pm2 start ecosystem.config.cjs --update-env`).
     - Validates and reloads Nginx (`nginx -t && systemctl reload nginx`).
   - Cleans up the temporary private key.

## 4. Production Code Optimizations Applied

During project analysis, several improvements were implemented to ensure production stability:

1. **Relative API Base URL (`frontend/src/services/api.js`):**
   Updated to use `import.meta.env.VITE_API_URL || (import.meta.env.PROD ? '/api' : 'http://localhost:5000/api')`. In production, requests use the relative `/api` path routed through Nginx, avoiding `ERR_CONNECTION_REFUSED localhost:5000`.
2. **Relative Media Upload Paths (`frontend/src/components/ProductCard.jsx`, `Cart.jsx`, `OrderDetails.jsx`, `ProductDetails.jsx`, `AdminOrderDetails.jsx`, `AdminProducts.jsx`):**
   Adjusted `getImageSrc` to check `import.meta.env.PROD ? imgPath : 'http://localhost:5000' + imgPath`. This ensures uploaded product images load properly on the live domain.
3. **Database URI Compatibility (`backend/config/db.js`):**
   Supports both `process.env.MONGO_URI` and `process.env.MONGODB_URI` seamlessly.
4. **Git Ignore Configuration (`.gitignore`):**
   Created root `.gitignore` to prevent uploading `node_modules/`, local `.env` files, and build directories to Git.
5. **Uploads Directory Retention (`backend/uploads/.gitkeep`):**
   Added `.gitkeep` so Git tracks the `uploads/` folder and server doesn't fail on file upload writes.

## 5. Step-by-Step Setup Guide (From Scratch)

Follow these steps to deploy the application:

### Step 1: Set Up Cloud Database (MongoDB Atlas)
1. Visit [MongoDB Atlas](https://cloud.mongodb.com/) and register or log in.
2. Create an **M0 Free Shared Cluster** (e.g. AWS provider in `us-east-1`).
3. Under **Security $\rightarrow$ Database Access**:
   - Click **Add New Database User**.
   - Create a user (e.g. `skincare_admin`) with a secure password.
4. Under **Security $\rightarrow$ Network Access**:
   - Click **Add IP Address**.
   - Click **Allow Access From Anywhere (`0.0.0.0/0`)** and Confirm.
   *(This is critical because EC2 instance public IP changes whenever restarted).*
5. Under **Deployment $\rightarrow$ Database**:
   - Click **Connect** $\rightarrow$ **Drivers** (Node.js).
   - Copy your connection string:
     ```
     mongodb+srv://<username>:<password>@<cluster>.mongodb.net/skincare_store?retryWrites=true&w=majority
     ```
   - Replace `<username>` and `<password>` with your database user credentials.

### Step 2: Start AWS Learner Lab & Get Credentials
1. Open your **AWS Learner Lab** (or AWS Academy / VocLabs console).
2. Click **Start Lab** and wait until the status indicator turns **green**.
3. Click **AWS Details** $\rightarrow$ Click **Show** next to AWS CLI.
4. Copy the values under `[default]`:
   - `aws_access_key_id`
   - `aws_secret_access_key`
   - `aws_session_token`

### Step 3: Initialize Git & Push to GitHub
If you haven't initialized Git yet, run these commands in the project root:

```bash
# 1. Initialize git repository
git init

# 2. Add all files (the .gitignore ensures node_modules & .env are excluded)
git add .

# 3. Create initial commit
git commit -m "feat(infra): configure CloudFormation, Nginx, PM2, and GitHub Actions CI/CD"

# 4. Set default branch to main
git branch -M main

# 5. Link your GitHub repository (replace with your repository URL)
git remote add origin https://github.com/<YOUR_GITHUB_USERNAME>/<YOUR_REPO_NAME>.git

# 6. Push to GitHub
git push -u origin main
```

### Step 4: Configure GitHub Secrets & Variables
In your GitHub repository, navigate to **Settings** $\rightarrow$ **Secrets and variables** $\rightarrow$ **Actions**:

#### 1. Repository Secrets (Click "New repository secret")
| Secret Name | Value | Description |
|---|---|---|
| `AWS_ACCESS_KEY_ID` | `ASIA...` | Copied from AWS Details in Step 2 |
| `AWS_SECRET_ACCESS_KEY` | `xxxx...` | Copied from AWS Details in Step 2 |
| `AWS_SESSION_TOKEN` | `FwoGZX...` (full long string) | Copied from AWS Details in Step 2 |
| `MONGODB_URI` | `mongodb+srv://...` | Full MongoDB connection string from Step 1 |
| `JWT_SECRET` | `skincare_super_secret_jwt_key_2026` | Any long secure random string |

#### 2. Repository Variables (Click "Variables" tab $\rightarrow$ "New repository variable")
| Variable Name | Value |
|---|---|
| `AWS_REGION` | `us-east-1` |

### Step 5: Automated Deployment Trigger
Once the secrets are saved:
1. Open the **Actions** tab in your GitHub repository.
2. Select **Deploy Web Application (CloudFormation + SSH)** on the left.
3. Click **Run workflow** (or simply push any commit to `main`).
4. The workflow will execute:
   - **Build Frontend:** Compiles and tests the React bundle (~30s).
   - **Deploy to EC2:** Deploys CloudFormation stack, generates SSH key pair, connects to the instance, pulls code, configures `.env`, builds, and reloads PM2/Nginx (~5–7 minutes on initial run).

### Step 6: Verify Live Website
When the deployment finishes with a green checkmark:
1. Click the completed workflow run.
2. Expand the step **Print Live Web Application URL**.
3. Click the URL (e.g. `http://54.x.x.x`) to view the live running skincare application!

## 6. Handling AWS Lab Expiration & 60-Second Recovery

In AWS Learner Lab environments, sessions automatically time out after 4 hours, which temporarily stops the EC2 instance and invalidates session credentials.

### How to Restore the Website in 60 Seconds:
1. Open your AWS Learner Lab and click **Start Lab**.
2. Once the indicator turns green, click **AWS Details** $\rightarrow$ **Show**.
3. Copy the updated values for `aws_access_key_id`, `aws_secret_access_key`, and `aws_session_token`.
4. Go to your GitHub repository $\rightarrow$ **Settings** $\rightarrow$ **Secrets and variables** $\rightarrow$ **Actions**.
5. Update `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN`.
6. Go to the **Actions** tab, select the latest run, and click **Re-run all jobs**.
7. CloudFormation automatically finds the existing stack, updates the instance IP, connects via SSH, and brings your site back online immediately.

## 7. Live Server Maintenance & Troubleshooting

To inspect the live server, open AWS EC2 Console, select the instance, and click **Connect $\rightarrow$ EC2 Instance Connect** (or SSH using the SSM key):

### Checking Application Health
```bash
# Check status of the backend Express app in PM2
pm2 status

# View live backend application logs (stdout & errors)
pm2 logs --lines 50

# Restart backend process with fresh environment variables
pm2 restart skincare-backend --update-env
```

### Inspecting Web Server (Nginx)
```bash
# Test Nginx configuration syntax
sudo nginx -t

# Reload Nginx without downtime
sudo systemctl reload nginx

# View real-time incoming HTTP access logs
sudo tail -f /var/log/nginx/access.log

# View Nginx error logs
sudo tail -f /var/log/nginx/error.log
```

### Seeding the Production Database (Optional)
If your application needs sample catalog data in MongoDB Atlas:
```bash
cd /var/www/app/backend
npm run seed
```
